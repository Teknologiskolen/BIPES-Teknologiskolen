# BIPES Pico W Programming and Runtime Control Architecture

## 1. Purpose

This document describes a proposed architecture for programming and controlling Raspberry Pi Pico W based robots from BIPES.

The goal is to let pupils program a robot using blocks while also making it possible to control and monitor the robot while it is running. The robot should support multiple communication methods, including USB serial, Bluetooth and Wi-Fi, while keeping the user experience simple and reliable.

The central design principle is:

> **Programming and runtime control are separate modes.**

Programming mode is used to upload, start, stop and reset programs.

Runtime mode is used to control and monitor the robot while the program is running.

The dashboard belongs to runtime mode only.

However, runtime mode is not limited to Bluetooth or Wi-Fi. Runtime dashboard control should also be possible over USB serial, as long as it uses a runtime message protocol and not the REPL protocol.

---

## 2. Background

The Raspberry Pi Pico W robot needs to support several activities:

1. Uploading programs generated from BIPES blocks.
2. Running the generated program on the Pico W.
3. Controlling the robot while the program is running.
4. Monitoring live data from the robot, such as sensors, motor state or status.
5. Supporting different communication methods:

   * USB serial REPL
   * Bluetooth REPL
   * Wi-Fi OTA upload
   * USB serial runtime control
   * Bluetooth runtime control
   * Wi-Fi MQTT runtime control

A problem appears if the same protocol is used for everything.

The MicroPython REPL is good for programming, uploading and starting scripts. However, it is not a good dashboard control protocol while a robot program is running. When the robot enters a continuous runtime loop, the REPL may be occupied or unavailable.

Therefore, BIPES should not use the REPL as the dashboard control protocol.

The better distinction is:

```text
REPL protocol:
    Used for programming and device management.

Runtime message protocol:
    Used by the dashboard while block.py is running.
```

This means that USB serial can still be used for dashboard control, but only if `block.py` contains a serial runtime receiver.

---

## 3. Core Design Principle

The architecture should separate the system into two main modes:

```text
Program Mode
    Used for:
    - generating code
    - uploading block.py
    - starting block.py
    - stopping/resetting the device
    - using serial REPL, Bluetooth REPL or Wi-Fi OTA

Runtime Mode
    Used for:
    - dashboard control
    - USB serial runtime control
    - Bluetooth RF control
    - Wi-Fi MQTT control
    - telemetry
    - live sensor values
    - emergency stop
```

The user should not have to think in terms of low-level transports. Instead, the user should interact with clear actions:

```text
Upload program
Run program
Stop program
Open dashboard
Drive with serial
Drive with Bluetooth
Control with Wi-Fi
Monitor robot
```

Internally, BIPES decides which transport and protocol should be used.

---

## 4. File Strategy

BIPES currently generates a file called:

```text
block.py
```

This should remain the default pupil-facing program file.

The generated file `block.py` contains the program created from blocks. It may also contain generated runtime support code, such as async tasks, serial runtime handlers, Bluetooth control handlers, MQTT handlers and telemetry logic.

The default model is:

```text
block.py = the pupil's generated robot program
```

The file `main.py` should only be used when needed.

Examples:

```text
Default:
    Upload and run block.py

If the user wants auto-run on boot:
    main.py imports block.py

If the user changes the filename:
    main.py imports the selected file
```

For example:

```python
# main.py
# Auto-generated by BIPES

import block
```

Or, if the user generated `line_follower.py`:

```python
# main.py
# Auto-generated by BIPES

import line_follower
```

This keeps `block.py` as the normal working file while still allowing the Pico W to auto-start a selected program.

---

## 5. Communication Architecture

BIPES should support several communication methods, but they should have clearly separated purposes.

### 5.1 Programming Channels

Programming channels are used to upload, start, stop or reset programs.

Supported programming channels:

```text
USB serial REPL
Bluetooth REPL
Wi-Fi OTA upload
```

These channels are used in Program Mode.

They are responsible for:

```text
- uploading block.py
- uploading helper files if needed
- starting block.py
- stopping/resetting the Pico W when the REPL is available
- optionally writing a main.py launcher
```

The dashboard should not send live control commands through the REPL.

---

### 5.2 Runtime Channels

Runtime channels are used when `block.py` is already running.

Supported runtime channels:

```text
USB serial runtime protocol
Bluetooth runtime protocol
Wi-Fi MQTT runtime protocol
```

These channels are used in Runtime Mode.

They are responsible for:

```text
- sending drive commands
- sending dashboard button commands
- receiving telemetry
- receiving sensor data
- showing robot status
- emergency stopping the robot
- sending runtime system commands
```

The dashboard is only active in Runtime Mode.

---

## 6. Serial Design

USB serial has two different roles.

### 6.1 Serial Program Mode

Serial Program Mode uses the MicroPython REPL.

It is used for:

```text
- uploading block.py
- running block.py
- stopping/resetting the Pico W through REPL commands
- reading normal terminal output
```

This is similar to how traditional MicroPython tools use serial communication.

---

### 6.2 Serial Runtime Mode

Serial Runtime Mode is different from Serial Program Mode.

When `block.py` is running, BIPES can use the same physical USB serial connection, but it should stop treating it as a REPL connection and instead treat it as a runtime message channel.

In this mode, the dashboard sends messages such as:

```text
D,40,40
S
LED,1
```

or:

```json
{"type":"drive","left":40,"right":40}
```

The running `block.py` must include a serial runtime receiver that reads these messages and dispatches them to the correct handlers.

The important distinction is:

```text
Bad:
    dashboard → serial REPL → Drive(40, 40)

Good:
    dashboard → serial runtime message → block.py dispatcher → Drive handler
```

So serial should support both programming and dashboard control, but not through the same protocol at the same time.

---

## 7. Bluetooth Design

Bluetooth has two different roles.

### 7.1 Bluetooth Program Mode

Bluetooth Program Mode uses the Bluetooth REPL.

It is used for:

```text
- uploading block.py
- running block.py
- stopping/resetting the Pico W when possible
```

This mode behaves like a wireless programming cable.

However, it should not be used for live dashboard control while the robot is running.

---

### 7.2 Bluetooth Runtime Control Mode

Bluetooth Runtime Control Mode is different from the Bluetooth REPL.

It should use a custom Bluetooth runtime service for small messages.

This mode is used for:

```text
- RF-style robot control
- joystick commands
- button commands
- live telemetry
- emergency stop
```

A simple design could be:

```text
BIPES Robot Control Service
    RX characteristic:
        BIPES writes commands to the robot

    TX characteristic:
        Robot sends telemetry and acknowledgements to BIPES
```

Example commands:

```text
D,40,40      # drive left motor 40, right motor 40
D,40,-40     # turn
S            # stop
LED,1        # turn LED on
```

The robot should include a safety timeout:

```text
If no drive command is received for 300–500 ms:
    stop motors
```

This prevents the robot from continuing to drive if the Bluetooth connection drops or the browser stops sending commands.

---

## 8. Wi-Fi Design

Wi-Fi also has two possible roles.

### 8.1 Wi-Fi OTA Programming

Wi-Fi OTA is used in Program Mode.

It allows BIPES to upload a new `block.py` without using a cable.

The reliable OTA upload flow should be staged:

```text
1. Upload block.py.tmp
2. Send checksum
3. Device verifies checksum
4. Stop current program safely
5. Rename block.py.tmp to block.py
6. Run or restart the program
7. Report success back to BIPES
```

This avoids destroying the last working program if the upload fails.

---

### 8.2 Wi-Fi MQTT Runtime Control

Wi-Fi MQTT is used in Runtime Mode.

It allows the dashboard and robot to communicate through MQTT topics.

Suggested topics:

```text
bipes/robots/{robot_id}/cmd
bipes/robots/{robot_id}/telemetry
bipes/robots/{robot_id}/status
bipes/robots/{robot_id}/ack
```

Example command:

```json
{
  "type": "drive",
  "left": 40,
  "right": 40,
  "seq": 183
}
```

Example telemetry:

```json
{
  "battery": 7.4,
  "distance_cm": 31,
  "mode": "running",
  "active_control": "mqtt"
}
```

MQTT is useful for classroom setups where several robots may be online at the same time.

---

## 9. Dashboard Responsibility

The dashboard should only be used in Runtime Mode.

The dashboard should not be active just because the device is connected through the REPL.

The dashboard becomes available when:

```text
- block.py is running
- the robot runtime has started
- a runtime channel is available
- telemetry or status is received
```

Possible dashboard states:

```text
Dashboard unavailable:
    Program has not been started.

Dashboard starting:
    Waiting for robot runtime.

Dashboard available:
    Runtime control connected.

Dashboard disconnected:
    Robot was stopped or connection was lost.
```

The dashboard may use:

```text
- USB serial runtime protocol
- Bluetooth runtime protocol
- Wi-Fi MQTT runtime protocol
```

The dashboard should not use:

```text
- USB serial REPL
- Bluetooth REPL
```

for live robot control.

## 10. Management Controls

Some buttons are not normal dashboard controls. They are management controls.

Examples:

```text
Reset device
Stop execution
Stop timers
Device info
Upload new program
```

These buttons may still be visible while the robot is running, but they must be state-aware.

The same button should behave differently depending on the current state of the robot.

### 10.1 Management Controls in Program Mode

In Program Mode, management controls use the programming channel.

Examples:

```text
Reset device:
    Send REPL reset or soft reset.

Stop execution:
    Send Ctrl-C through REPL.

Device info:
    Ask the REPL for device information.

Upload new program:
    Upload block.py through serial REPL, Bluetooth REPL or Wi-Fi OTA.
```

### 10.2 Management Controls in Runtime Mode

In Runtime Mode, management controls should first use runtime system commands.

Examples:

```text
Reset device:
    Send runtime message: system.reset

Stop execution:
    Send runtime message: system.stop

Stop timers:
    Send runtime message: system.stop_timers

Device info:
    Send runtime message: system.info
```

The running `block.py` must include handlers for these built-in system messages.

Example messages:

```json
{
  "type": "system.stop"
}
```

```json
{
  "type": "system.reset"
}
```

```json
{
  "type": "system.info"
}
```

## 11. REPL Fallback Strategy

Runtime system commands should be the preferred way to stop or reset a running robot.

However, BIPES should also have a fallback strategy.

Recommended order when the robot is running:

```text
1. Send runtime system command over the active runtime channel.
2. Wait for acknowledgement.
3. If no acknowledgement is received, try another available runtime channel.
4. If that fails and a REPL connection is available, try REPL fallback.
5. If that fails, ask the user to physically reset or reconnect the device.
```

Example for Stop Execution:

```text
1. Send system.stop over serial runtime, Bluetooth runtime or MQTT.
2. Wait for ack: stopped.
3. If no ack, try REPL Ctrl-C if connected.
4. If Ctrl-C fails, try REPL soft reset.
5. If that fails, show recovery instructions.
```

Example for Reset Device:

```text
1. Send system.reset over the runtime channel.
2. Runtime stops motors and calls machine.reset().
3. If no ack or disconnect occurs, attempt REPL reset if possible.
4. If that fails, ask the user to press the physical reset button or reconnect.
```

This makes management buttons reliable while still respecting the separation between Program Mode and Runtime Mode.

---

## 12. Runtime State-Aware Commands

BIPES commands must be aware of the robot state.

A button like `Reset device` cannot always do the same thing.

Example:

```text
If robot is in Program Mode:
    Reset device → send REPL reset.

If robot is in Runtime Mode:
    Reset device → send runtime system.reset.

If runtime reset fails:
    fallback to REPL reset if possible.
```

Suggested BIPES states:

```text
DISCONNECTED
PROGRAM_CONNECTED
UPLOADING
PROGRAM_READY
RUNNING
RUNTIME_READY
DASHBOARD_CONNECTED
SAFE_STOPPING
ERROR_RECOVERY
```

Every action should be routed based on the current state.

---

## 13. Runtime Message Handling in block.py

Because the dashboard exists in Runtime Mode, the generated `block.py` must be able to receive runtime messages while the robot is running.

This means `block.py` should include:

```text
- robot control loop
- serial runtime receiver task if serial dashboard is enabled
- Bluetooth runtime receiver task if Bluetooth dashboard is enabled
- MQTT runtime receiver task if MQTT dashboard is enabled
- command dispatcher
- built-in system command handlers
- user-defined dashboard command handlers
- telemetry task
- safe stop logic
```

However, pupils should not need to manually build all of this from blocks.

BIPES should automatically generate the runtime receive/dispatch system when the user enables dashboard control, Bluetooth control, serial runtime control or MQTT control.

---

## 14. Built-In System Commands

Some runtime commands should always be built into the generated runtime code.

These should not depend on pupil-created blocks.

Recommended built-in system commands:

```text
system.stop
system.reset
system.info
system.status
system.stop_timers
emergency_stop
release_control
```

Example behavior:

```text
system.stop:
    Stop motors.
    Cancel or exit runtime tasks.
    Exit block.py if possible.
    Return to Program Mode if possible.

system.reset:
    Stop motors.
    Send acknowledgement if possible.
    Call machine.reset().

system.info:
    Return device name, program name, runtime state and enabled channels.

emergency_stop:
    Stop motors immediately.
    Keep runtime alive if possible.

release_control:
    Release the active dashboard controller.
```

These commands make the system safer and more predictable.

---

## 15. User-Defined Dashboard Commands

Pupil blocks should define custom dashboard behavior, not the low-level communication system.

Example blocks:

```text
When dashboard button "LED" is pressed:
    turn LED on

When joystick changes:
    set left motor speed
    set right motor speed

Every 500 ms:
    send distance sensor value to dashboard
```

Internally, BIPES can generate handlers:

```python
USER_HANDLERS = {
    "drive": on_drive,
    "led": on_led,
}
```

The runtime dispatcher receives messages and calls the correct handler.

Example:

```python
def dispatch_runtime_message(ctx, msg):
    msg_type = msg["type"]

    if msg_type.startswith("system."):
        handle_system_command(ctx, msg)
        return

    if msg_type in USER_HANDLERS:
        USER_HANDLERS[msg_type](ctx, msg)
```

## 16. Active Controller Lock

If several runtime channels are enabled at the same time, the robot must avoid being driven by multiple controllers at once.

For example, a robot should not receive drive commands from Bluetooth and MQTT at the same time without a rule.

Suggested state:

```text
active_control = none
active_control = serial
active_control = bluetooth
active_control = mqtt
```

Rules:

```text
- First controller to request control becomes active.
- Other controllers may monitor telemetry.
- Other controllers cannot drive unless control is released or timed out.
- Emergency stop is always accepted from any channel.
- Control expires after a timeout.
- Controller can release control.
```

This makes it possible to support several runtime transports without making the robot unpredictable.

---

## 17. Safety and Reliability

Reliability is important because pupils may disconnect devices, close browser tabs, lose Bluetooth connection or upload broken programs.

The system should include:

```text
- motor timeout
- emergency stop
- staged file upload
- checksums for OTA
- acknowledgement messages
- active controller lock
- safe program restart
- clear dashboard states
- REPL fallback for management actions
```

### 17.1 Motor Timeout

The robot should stop automatically if it does not receive drive commands for a short period.

Example:

```text
If no runtime drive command is received for 500 ms:
    stop motors
```

### 17.2 Emergency Stop

Emergency stop should be accepted from any runtime channel.

Even if Bluetooth has active control, a serial or MQTT emergency stop should still be allowed.

### 17.3 Safe Upload While Running

If the user wants to upload a new program while the robot is running, BIPES should first stop the runtime safely.

Recommended flow:

```text
1. Send system.stop through the active runtime channel.
2. Wait for acknowledgement.
3. If no acknowledgement, use fallback.
4. Once stopped, switch to Program Mode.
5. Upload the new block.py.
6. Run the new block.py.
7. Reconnect dashboard runtime channel if needed.
```

## 18. User Flows

### 18.1 Serial Programming + Serial Dashboard Runtime

This is useful when the robot is connected by USB cable.

```text
1. User connects Pico W with USB.
2. BIPES enters Serial Program Mode.
3. User creates a block program.
4. BIPES generates block.py.
5. BIPES uploads block.py over serial REPL.
6. User presses Run.
7. block.py starts on the Pico W.
8. BIPES switches the same serial connection to Serial Runtime Mode.
9. Dashboard becomes available.
10. User controls the robot from the dashboard over serial runtime messages.
```

This gives dashboard control even without Bluetooth or Wi-Fi.

---

### 18.2 Serial Programming + Bluetooth Runtime Control

This is a good beginner wireless driving flow.

```text
1. User connects Pico W with USB.
2. BIPES enters Program Mode.
3. User creates a block program.
4. BIPES generates block.py.
5. BIPES uploads block.py over serial REPL.
6. User presses Run.
7. block.py starts on the Pico W.
8. BIPES switches to Runtime Mode.
9. Dashboard becomes available.
10. User connects Bluetooth runtime control.
11. User drives the robot from the dashboard.
```

This is reliable because USB serial is used for programming, while Bluetooth is used for live control.

---

### 18.3 Bluetooth Programming + Bluetooth Runtime Control

This flow is fully wireless, but BIPES must clearly separate the two Bluetooth modes.

```text
1. User selects Bluetooth Program Mode.
2. BIPES connects through Bluetooth REPL.
3. BIPES uploads block.py.
4. User presses Run.
5. BIPES disconnects from Bluetooth REPL.
6. The robot starts its Bluetooth runtime control service.
7. User opens the dashboard.
8. BIPES connects to Bluetooth Runtime Control Mode.
9. User drives the robot.
```

Important distinction:

```text
Bluetooth Program Mode = BLE REPL
Bluetooth Runtime Mode = custom BLE control service
```

The same physical Bluetooth radio is used, but the communication mode is different.

---

### 18.4 Wi-Fi OTA Programming + Wi-Fi MQTT Runtime Control

This is the most complete wireless classroom setup.

```text
1. Robot is already configured for Wi-Fi.
2. BIPES enters Program Mode.
3. User generates block.py.
4. BIPES uploads block.py using OTA.
5. Robot verifies and starts the new program.
6. block.py connects to MQTT.
7. BIPES switches to Runtime Mode.
8. Dashboard connects through MQTT.
9. User controls and monitors the robot.
```

This flow is useful when robots should be programmed and monitored without cables.

---

### 18.5 Serial or Bluetooth Programming + Wi-Fi MQTT Runtime Control

This is a useful middle-ground flow.

```text
1. User uploads block.py using serial REPL or Bluetooth REPL.
2. User starts block.py.
3. block.py connects to Wi-Fi.
4. block.py connects to MQTT.
5. BIPES switches to Runtime Mode.
6. Dashboard controls and monitors the robot through MQTT.
```

This allows reliable programming over REPL while using Wi-Fi for live runtime communication.

---

### 18.6 Wi-Fi OTA Programming + Bluetooth Runtime Control

This flow is useful for small RF-style robots.

```text
1. Robot is already available over Wi-Fi.
2. BIPES uploads block.py using OTA.
3. Robot starts block.py.
4. Robot advertises Bluetooth runtime control.
5. User opens the dashboard.
6. User drives the robot over Bluetooth.
7. Wi-Fi may still be used for logs or status.
```

This combines wireless programming with low-latency Bluetooth driving.

---

## 19. Runtime State Machine

BIPES should use a clear state machine so that mode switching is reliable.

Suggested states:

```text
DISCONNECTED
    ↓
PROGRAM_CONNECTED
    ↓
BLOCKS_GENERATED
    ↓
UPLOADING_BLOCK_PY
    ↓
PROGRAM_READY
    ↓
RUNNING_BLOCK_PY
    ↓
RUNTIME_READY
    ↓
DASHBOARD_CONNECTED
```

When the user wants to upload a new program while the robot is running:

```text
DASHBOARD_CONNECTED
    ↓
SAFE_STOP_RUNTIME
    ↓
PROGRAM_CONNECTED
    ↓
UPLOADING_BLOCK_PY
    ↓
RUNNING_BLOCK_PY
    ↓
RUNTIME_READY
    ↓
DASHBOARD_CONNECTED
```

The robot should always enter a safe state before switching back to Program Mode.

## 20. Suggested block.py Structure

The generated `block.py` can contain several sections.

```python
# ============================================================
# BIPES GENERATED ROBOT PROGRAM
# File: block.py
# ============================================================

# 1. Imports
# 2. Runtime context
# 3. Communication setup
# 4. Built-in system command handlers
# 5. User block code
# 6. Async tasks
# 7. Start program
```

Example structure:

```python
import asyncio
import time
from machine import Pin
import machine

class RobotContext:
    def __init__(self):
        self.running = True
        self.active_control = None
        self.last_command_ms = time.ticks_ms()
        self.left_speed = 0
        self.right_speed = 0

    def command_seen(self, channel):
        self.last_command_ms = time.ticks_ms()
        if self.active_control is None:
            self.active_control = channel

    def command_timed_out(self, timeout_ms=500):
        return time.ticks_diff(time.ticks_ms(), self.last_command_ms) > timeout_ms

    def stop_motors(self):
        self.left_speed = 0
        self.right_speed = 0
        # Actual motor stop code goes here


def handle_system_command(ctx, msg):
    msg_type = msg["type"]

    if msg_type == "system.stop":
        ctx.stop_motors()
        ctx.running = False

    elif msg_type == "system.reset":
        ctx.stop_motors()
        machine.reset()

    elif msg_type == "emergency_stop":
        ctx.stop_motors()

    elif msg_type == "release_control":
        ctx.active_control = None


led = Pin("LED", Pin.OUT)

def on_drive(ctx, msg):
    ctx.command_seen(msg.get("channel", "unknown"))
    ctx.left_speed = msg["left"]
    ctx.right_speed = msg["right"]

def on_led(ctx, msg):
    if msg["value"] == 1:
        led.on()
    else:
        led.off()


USER_HANDLERS = {
    "drive": on_drive,
    "led": on_led,
}


def dispatch_runtime_message(ctx, msg):
    msg_type = msg["type"]

    if msg_type.startswith("system.") or msg_type == "emergency_stop":
        handle_system_command(ctx, msg)
        return

    if msg_type in USER_HANDLERS:
        USER_HANDLERS[msg_type](ctx, msg)


async def motor_task(ctx):
    try:
        while ctx.running:
            if ctx.command_timed_out(500):
                ctx.stop_motors()

            # Apply motor speeds here

            await asyncio.sleep_ms(20)
    finally:
        ctx.stop_motors()


async def serial_runtime_task(ctx):
    while ctx.running:
        # Read serial runtime messages and call dispatch_runtime_message(ctx, msg)
        await asyncio.sleep_ms(10)


async def bluetooth_runtime_task(ctx):
    while ctx.running:
        # Process Bluetooth runtime messages and call dispatch_runtime_message(ctx, msg)
        await asyncio.sleep_ms(10)


async def mqtt_runtime_task(ctx):
    while ctx.running:
        # Process MQTT runtime messages and call dispatch_runtime_message(ctx, msg)
        await asyncio.sleep_ms(10)


async def telemetry_task(ctx):
    while ctx.running:
        # Send telemetry over enabled runtime channels
        await asyncio.sleep_ms(250)


async def main():
    ctx = RobotContext()

    asyncio.create_task(motor_task(ctx))
    asyncio.create_task(telemetry_task(ctx))

    # Only include these if enabled by the blocks/settings:
    asyncio.create_task(serial_runtime_task(ctx))
    asyncio.create_task(bluetooth_runtime_task(ctx))
    asyncio.create_task(mqtt_runtime_task(ctx))

    while ctx.running:
        await asyncio.sleep_ms(100)


asyncio.run(main())
```

In the final implementation, serial, Bluetooth and MQTT logic should be generated only when the user enables those features or adds dashboard/runtime blocks.

## 21. BIPES User Interface

The user interface should make the mode split clear.

A possible device card:

```text
Robot: PicoW-23A1

Program Mode:
    Connection: USB serial connected
    File: block.py
    Status: Ready

Runtime Mode:
    Dashboard: Not running
    Serial runtime: Disconnected
    Bluetooth control: Disconnected
    MQTT: Offline

Actions:
    Upload block.py
    Run
    Stop execution
    Reset device
    Open dashboard
    Drive with serial
    Drive with Bluetooth
    Control with Wi-Fi
```

When the robot is running:

```text
Robot: PicoW-23A1

Program Mode:
    Connection: inactive while running

Runtime Mode:
    Dashboard: Active
    Serial runtime: Connected
    Bluetooth control: Connected
    MQTT: Online
    Active controller: Bluetooth

Actions:
    Emergency stop
    Release control
    Stop execution
    Reset device
    Upload new program
```

The UI should guide the user through mode changes instead of exposing all technical details.

## 22. Recommended Development Order

A practical implementation order would be:

```text
1. Keep block.py as the default generated file.
2. Add a clear Program Mode / Runtime Mode state machine in BIPES.
3. Support serial upload and run block.py reliably.
4. Add asyncio-based generated robot programs.
5. Add serial runtime dashboard control.
6. Add built-in runtime system commands.
7. Add Stop Execution and Reset Device with runtime-first, REPL-fallback behavior.
8. Add motor timeout and emergency stop.
9. Add dashboard states based on runtime connection.
10. Add Bluetooth runtime control for RF-style driving.
11. Add active controller lock.
12. Add Wi-Fi MQTT runtime control.
13. Add Wi-Fi OTA upload with staged block.py.tmp updates.
14. Add Bluetooth REPL programming as optional.
15. Add main.py launcher only for auto-run or custom filenames.
```

The most important early milestone is:

```text
Reliable separation between Program Mode, Runtime Mode and protocol routing.
```

Once this is in place, additional transports can be added without confusing the user.

## 23. Final Architecture Summary

The final architecture can be summarized as:

```text
BIPES
├── Block editor
│   └── generates block.py
│
├── Program Mode
│   ├── USB serial REPL upload
│   ├── Bluetooth REPL upload
│   └── Wi-Fi OTA upload
│
└── Runtime Mode
    └── Dashboard
        ├── USB serial runtime control
        ├── Bluetooth RF control
        ├── Wi-Fi MQTT control
        ├── telemetry
        ├── sensor monitoring

```

On the Pico W:

```text
block.py
├── generated user program
├── async robot control loop
├── serial runtime receiver task
├── Bluetooth runtime control task
├── MQTT runtime control task

```

`main.py` is optional and should only be used as a small launcher when the user wants auto-run or has selected a custom file name.

## 24. Main Design Rules

The most important rules are:

```text
The REPL is for programming.
The dashboard is for runtime.
Serial can be used for both, but not with the same protocol at the same time.
Management buttons are state-aware.
Runtime commands are tried first.
REPL fallback is used only if runtime commands fail or runtime is unavailable.
```

This means:

```text
Serial REPL:
    upload, run, stop, reset in Program Mode

Bluetooth REPL:
    upload, run, stop, reset in Program Mode

Wi-Fi OTA:
    upload, replace, restart in Program Mode

Serial runtime protocol:
    dashboard control and telemetry in Runtime Mode

Bluetooth runtime protocol:
    dashboard control and telemetry in Runtime Mode

Wi-Fi MQTT:
    dashboard control and telemetry in Runtime Mode
```

This gives pupils a simple experience while making the system reliable internally.
